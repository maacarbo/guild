# Guild — Roadmap

*Repositioned 2026-07-29 (see ARCHITECTURE.md D8); reorganised 2026-07-30 (operator directive: functionality and ease of setup/test first, milestone after milestone, until the full valuable product exists — deployment types only after; Kubernetes last, optional, and strictly generic). The original six-milestone platform roadmap is in git history; milestones below supersede it.*

**Audience note (2026-07-30, revised):** milestones are the **author's execution plan** — but each milestone's *deliverables* are the portable artifacts other users install: M1 ships the Tier 1 compose quickstart, M2 ships `v0.1.0` on it, M3 ships team evolution on the same stack (`v0.2.0` — the feature-complete product: all three PRODUCT.md success criteria met), and the optional M4 ships the generic Tier 2 K8s manifests only if a recorded need exists. No bullet in this roadmap names author-specific infrastructure; the author's cluster material (Talos, Cilium, NFS, Flux, ESO) was extracted to a personal runbook (`docs/runbooks/authors-cluster.md`) — a worked example, required for nobody, normative for nothing.

**Sequencing decision (operator, 2026-07-30 reorganisation; supersedes the same-day compose-first note and the kubectl-dev-namespaces plan): functionality first, deployment types last, Kubernetes last of all.** The full product — team evolution included — is built, working, and **shipped on Docker Compose** (M1–M3). The governance loop *and* team evolution are functionally identical on compose — gates, contracts, `docker run` validator sandboxes, gateway `max_budget` caps, hiring via Multica's REST surface — so a cluster can only ever add operational qualities, never features; Kubernetes is therefore the optional last milestone (M4), generic-only, pursued only if possible/needed.

## M1 — Substrate proven (on Docker Compose)

Nothing in Guild matters if the substrate assumptions don't hold; prove them first — entirely on the compose stack. (History: the external review split M1 into phases; the Anthropic review moved the proof to the workstation; the 2026-07-30 sequencing decision made compose the primary target through M2, moving the cluster lift to M3; the 2026-07-30 reorganisation extended compose through M3 — team evolution — and made the cluster lift the optional M4.)

### M1a — Capability proof

- Compose stack: pinned Multica + isolated LiteLLM; scratch GitHub repo. **Deliverable: this compose stack is the shipped Tier 1 quickstart** (`deploy/README.md`) — new users install what the milestone proves
- Daemon container e2e (amd64, creds at runtime; Claude Code at the time of the probe — image scope now OpenCode default + Claude Code per D9, 2026-07-30): claims + completes a task, pushes an engagement branch
- Gateway proofs: prompt caching + extended thinking via LiteLLM logs/headers; **virtual key minted with `max_budget` stops serving at cap** — record how the 429 classifies in Multica
- Spend attribution: per-engagement key → task → attributable spend read back
- API probes: issue create/assign/comment/cancel; **cancel kills the forked CLI and stops gateway traffic**; WS events (+ REST read endpoints for reconciliation); **does a top-level conductor-PAT comment trigger the implementing agent** (bounce delivery — currently unverified and load-bearing); **do replies on closed issues still enqueue tasks** (termination protocol); **does bounce survive a daemon restart** (continuity floor); agent/squad management endpoints (**best-effort** — the idle-pool fallback stands either way; the result feeds M3 team evolution directly)
- Concurrency probes (added 2026-07-30 — the frozen investigation verified neither): **does one daemon run claimed tasks in parallel or serialized**; **do two daemon containers register as distinct runtimes end-to-end** (the per-task RuntimeID binding is verified-in-code; multi-daemon registration is inference until probed). Pre-declared fallback if the daemon serializes: one compose daemon service per busy role, each with its own `mdt_` token and anonymous workspace volume — a compose-file change, not a design change
- Ease-of-setup deliverables (directive clause 1; **respecified 2026-07-31 — cross-platform ruling**: the only tool every user is guaranteed to have is Docker itself; `make` and host shell scripts are Unix-only and are **dropped from the design** — no second PowerShell implementation to maintain, ever): `deploy/compose/.env.example` with the four normative secret sections, each var commented with its source and owning secret — only **two user-typed external credentials** exist (one model-provider key — `OPENROUTER_API_KEY` recommended per D9, `ANTHROPIC_API_KEY` optional for the direct route — and the scoped git PAT); generated secrets are documented as "any long random string" (no generator dependency). **Setup is docs-first and UI-first**: the quickstart walks the two-phase boot — control plane up → mint the `mul_` PAT in Multica's UI and the virtual key in LiteLLM's admin UI (`/ui`) → daemon up — in **compose verbs only** (`docker compose up -d` / `--profile daemon up -d` / `down -v`); the bootstrap-ordering trap is documented, not scripted. Testing/probes default to the gateway's cheap tier (`or-deepseek-v3-2`, `or-gemini-flash-lite`), not frontier models. **The one automation deliverable is the doctor**: the capability probes ship as a one-shot compose service — `docker compose run --rm doctor` — a single implementation running in a Linux container (host OS irrelevant), where every failure names the broken prerequisite, the fix, and the owning secret. The M2 `guild` CLI absorbs setup as `guild init` (per-engagement keys already remove the static daemon key by then). First-user creation scriptable: **PROVEN** (matrix P2)

#### Standing M1–M3 rules

- **Compose-first dev** — everything runs as an isolated compose project on the workstation; no cluster dependency exists anywhere in M1–M3. Pinned Multica version; record the LICENSE-diff review procedure with the pin; **one versions file** (Multica version, LiteLLM digest, CLI versions) consumed by the compose file, the daemon-image build args, and doctor — README, compose, and image can never silently disagree.
- **Full isolation — test like a new user**: zero pre-existing services from the author's environment (the concrete exclusion list moved to the personal runbook). Dev gateway = isolated LiteLLM, cloud routes only, own DB for virtual keys/spend; local-model backends documented as an option.
- Datastores: **containerized mode implemented** (Multica pgvector Postgres, LiteLLM DB, Guild Postgres as compose services with named volumes); **external mode documented-only** (connection-string overrides) until M4 exercises it. Backup discipline is compose-era, not cluster-era: from M2, nightly `pg_dump` of Guild PG + LiteLLM DB via host cron or a scheduler container — governance provenance and spend records are the backup-worthy data.
- **Compose-era hardening floor (raised 2026-07-30):** segmented compose networks as trust zones (all databases `internal: true`; daemon and validator reach only the Multica backend + gateway), non-root containers, `cap_drop: ALL` + `no-new-privileges`, memory/pids limits on daemon and validator containers, no unnecessary host mounts, a **fine-grained git PAT scoped to the product repo(s) only**, `.env` files gitignored and `chmod 600`. The real blast-radius bounds remain the explicit-approval default and the gateway `max_budget` caps. What plain Docker cannot provide — kernel sandboxing, FQDN egress control — is a **documented residual risk** stated in the `deploy/README.md` security floor; the Kubernetes controls land with the optional M4 lift, if pursued.
- Tier 1 validator driver: the conductor reaches the Docker API **only through a scoped socket proxy** — never a raw `/var/run/docker.sock` mount; the Tier 1 egress deviation is documented in ARCHITECTURE.md D6.

**M1a exit criteria:** every probe/build item above has a recorded pass/fail entry in the **capability matrix** (`docs/research/`), including explicit failure-path behavior: failed token login, missing CLI, proxy-unsupported features, WS disconnect mid-task. A failed item with a documented workaround still exits; an untested item does not. **Ease bar (directive clause 1):** a fresh machine with only Docker + the two user-typed credentials reaches a healthy stack with `docker compose run --rm doctor` green in ≤ 15 min, ≤ 5 manual steps, zero undocumented steps — on Windows, macOS, and Linux alike (the quickstart uses compose verbs only).

### M1b — Contracts & adapter shaping

- `packages/shared` v2 contracts (governance events, contract execution semantics, substrate error categories, port reads/rework/close — landed 2026-07-30) refined against the M1a capability matrix
- `substrate-multica` adapter for the verified endpoints, TDD per CLAUDE.md with the `ExecutionSubstrate` port contract-test suite; adapter errors mapped to the stable `SubstrateErrorCategory` set; the suite doubles as the **substrate conformance suite** — mandatory-green on every Multica pin bump and daemon image rebuild
- Startup config validation is atomic: the conductor lists **every** missing/invalid env var with its owning normative secret before exiting; the `SubstrateErrorCategory` → operator-action map turns raw faults into named fixes (budget-capped 429 surfaces as "engagement budget cap reached", per the M1a classification finding)
- **First proof of the core mechanism**: validate a hand-written `HandoffContract` against the branch the integration test produced (SHA-pinned, validator-sandbox pattern via the `docker run` driver) — the differentiator gets its first demonstration here, not in M2

**M1b exit criteria (= M1 acceptance):** a Guild integration test creates an issue via the port on the compose stack, a containerized daemon agent completes it, the engagement branch lands in the scratch repo, comment/status events arrive over WS, the spend appears in LiteLLM **attributed to the engagement's virtual key**, and a hand-written contract validates against the produced branch (via the `docker run` validator driver). **"Scripted, no manual steps" means: one idempotent entrypoint run over standing infrastructure** — it may assume the compose stack is up; it may not assume any prior test state. The same entrypoint ships as **`make smoke`** and passes twice consecutively *without* a reset in between (idempotency proven, ≤ 10 min per run).

## M2 — Core governance loop (split 2026-07-30, Anthropic review: the differentiator gets a proof point before the whole product)

### M2a — One real engagement, governed

- Hand-authored `StagePlan` (no planner yet): one stage, one role, one engagement
- Full governed path: explicit gate → saga dispatch (virtual key with `max_budget`, brief, contract) → agent works → SHA-pinned validator-sandbox validation → **a real bounce with a real fix** → fast-forward merge → accept → termination protocol
- Reconciliation proven: kill the conductor mid-engagement, restart, watch it recover from reads

**M2a acceptance:** one engagement completes the entire governed lifecycle including one genuine bounce-and-recover, with every transition in the `decisions` table.

### M2b — The planner and the team

- Stage planner: idea → staged plan (analysis → architecture → implementation → test → delivery) with roles and budget allocation; plan versioning + re-gate on amendment
- Plan-approval gate via CLI — explicit approval by default, auto-approve timer as per-project opt-in (open question 2: decide comment-mirror UX from use)
- Fixed starter team of four roles; multi-stage, multi-engagement orchestration (role-memory artifacts deferred wholesale to M3 — briefs carry `priorDecisions` explicitly until then)
- Budget watchdog (application code — needs no cluster): per-engagement soft cap (warn) and per-project hard cap (cancel via substrate + lock dispatch), metered from the LiteLLM gateway; an induced overspend halts the pipeline cleanly with a visible explanation

**M2 acceptance — the full application, working and shipped:** a demo idea produces a repo with passing tests where every stage was gated and every handoff contract-validated — zero un-contracted advances; the run's decision trail is queryable from Guild's `decisions` table; an induced overspend halts cleanly. **Ship it: tag `v0.1.0` and publish the Tier 1 quickstart** — anyone with Docker, API keys, and a git token can run Guild. Ship-gate additions (2026-07-30): **publish the daemon image to a public registry** so the quickstart pulls instead of builds (deployment-neutral — pulled forward from the old K8s milestone; the upstream-contribution framing travels with it); ship **`guild demo`** — the M2 acceptance fixture with its measured cost and wall-clock recorded at M2a, so the first governed engagement is a known-good path at a known price; **fresh-machine bar**: a new user following only the published docs reaches the accepted demo engagement in ≤ 30 min wall-clock and ≤ 2× the recorded demo cost, with the README quickstart executed verbatim as the acceptance script; `docker compose down -v` → full quickstart replay goes green.

## M3 — Team evolution (on the compose stack) — the feature-complete product

Moved up from M4 (operator reorganisation 2026-07-30): this milestone completes PRODUCT.md success criterion 3, and a feature-bearing milestone cannot sit behind a feature-free one. Everything here is Multica REST calls, registry data, and conductor application code — no bullet requires any cluster primitive; the residual unknowns (management-API surface, daemon concurrency, multi-daemon registration) are substrate properties identical on any deployment and are already M1a probes.

- Dynamic hiring: Guild creates/configures Multica agents and squads on demand from role templates (contingent on the M1 API probe; **pre-declared fallback**: selection from a pre-registered idle pool of role agents if runtime creation is unusable — same product outcome. Precision (2026-07-30 refutation): the fallback avoids the unverified agent-*creation* surface, but its assignment mechanics are themselves part of the M1a core-loop probes — "known-supported" applies to manual registration only)
- Role-template registry + capability selection as data; retire idle agents. **v1 hiring is constrained to runtimes already baked into the daemon image** — adding a runtime stays the documented three-move image procedure (OVERVIEW.md), never a hiring side effect
- Role-memory artifact maintenance across engagements — closes M2b's explicit deferral: briefs stop carrying `priorDecisions` by hand
- Governance provenance: hire and retire decisions are appended to the `decisions` table
- Conformance-suite extension: assertions for whichever agent-management surface the milestone actually uses (registry create/retire endpoints, or idle-pool selection mechanics) — mandatory-green on pin bumps like the rest of the M1b suite
- Floor inheritance (2026-07-30): hired agents inherit the compose hardening floor — same daemon image, same segmented networks, no new credential classes — and every hired-agent engagement gets a per-engagement virtual key minted with `max_budget`, so the budget insurance scales with the team by construction. Concentration note: one daemon runs the whole team as sibling subprocesses; the documented mitigation is daemon-per-role compose services (see the M1a multi-daemon probe) — a compose-file change, not a design change

**Acceptance:** on the Tier 1 compose stack, a role not present at project start is hired because the plan demanded it, completes contracted work (gated, contract-validated, spend-capped by its engagement key), and is retired — all visible on the Multica board; a second engagement of the same role receives the role-memory artifact the first one updated; hire/retire rows are queryable in `decisions`; the extended conformance suite is green; no new infrastructure classes introduced; the M2 fresh-machine bar still holds. The acceptance holds under the fallback path too. **Ship it: tag `v0.2.0` — all three PRODUCT.md success criteria are now demonstrably met, on the tier anyone can run.**

## M4 — Deployment options (optional, last): generic Kubernetes

**Entry condition:** `v0.2.0` shipped **and** a recorded need beyond Tier 1 — user demand, or a gap found by the requirements audit at M3 close. Absent that, the milestone closes with the verdict recorded and only the unconditional item executed. Strictly generic: any cluster, vanilla assumptions, zero author-cluster material (that lives in the personal runbook, outside this roadmap).

- Unconditional (deployment-agnostic — deliberately not hostage to the K8s conditional): first real exercise of the **external-datastore mode** (connection-string overrides, one DB + one role per app, pgvector required for Multica) — valuable on compose alone for users with existing Postgres
- Conditional — lift the proven compose stack to Kubernetes; re-validate the capability matrix's transport rows (WS through cluster networking, PVC-backed volumes) **once, against the final post-M3 capability surface**. **Deliverable: the Tier 2 generic K8s manifests** — vanilla assumptions only: any default StorageClass or external datastores, plain-`kubectl` secrets under the normative names, validator sandboxes as K8s Jobs via the existing second driver; no CNI, runtime, ingress, or GitOps assumptions
- Conditional — hardening expressed as generic requirements, with documented residual risk where an environment lacks them: deny-by-default FQDN egress where the CNI supports it; non-privileged SAs with `automountServiceAccountToken: false`; PSA `restricted`; the narrower scoped `mdt_` token; RuntimeClass sandboxing (gVisor/Kata) where available; LiteLLM hardened per D2; storage per the generic ground rules (single-replica `Recreate` Postgres, nightly `pg_dump` CronJob, `emptyDir` workspaces)

**Acceptance (if the lift is pursued):** the M2 demo flow passes on a disposable vanilla cluster (kind or k3s) installed from the published generic manifests alone; transport rows re-validated green. **Either way:** the external-datastore mode is proven, and the entry-condition verdict — demand evidence or its absence — is recorded at milestone close.
